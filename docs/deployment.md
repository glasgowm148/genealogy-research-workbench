# Build and deployment

## Configure your project

`genealogy init` creates `genealogy.toml`. Change `[project].name` to your public project title. An optional description is supported:

```toml
[site]
description = "Our family history, its records, and the questions still open."
```

The title/description are public. Keep private personal information out of them. When the site will live at a known address, set it so the build also writes an XML sitemap and canonical links:

```toml
[site]
base_url = "https://example.org/family/"
```

To invite corrections, give a contact. With one set, the build adds a **Corrections** page (`corrections.html`, linked from the menu and every footer) explaining what a useful correction contains, and each person's page gains a **Suggest a correction** link:

```toml
[site]
contact_email = "corrections@example.org"            # one address
contact_url = "https://example.org/family/contact"  # https only
corrections_note = "Replies can take a few weeks."   # optional, shown as written
```

Either contact is enough. With `contact_email`, the person's link opens an email whose subject is `Correction: <name> (<record ID>)`; with `base_url` also set, the message starts with the page address. With only `contact_url`, the link leads to the Corrections page. The contact is taken only from these settings, never from the case, and it is public: use an address you are happy to publish. `corrections_note` is used only when a contact is set. Remove the settings and rebuild to take the page and links down.

When a site has more than one record type, the sources page groups sources by their recorded `source_type`, printed as written with a capital first letter ("Parish register"); types written in different styles, such as `parish_register` and "Parish register", are one type. To give a type a reader's label, or a caution printed at the top of its section, add a table per type. The key uses lower-case letters, digits, `_` or `-`, and each table takes `label`, `note` or both:

```toml
[source_types.banns]
label = "Marriage banns"
note = "Banns alone do not prove a wedding took place."
```

To list possible duplicate people for checking, switch on the **Possible duplicates** page (`duplicates.html`, linked from the menu). It is off by default, so a small or tidy site is not given an empty or noisy page:

```toml
[research]
duplicates = true   # a TOML boolean, not "true"
```

The page pairs public people who have the same surname (spellings listed under `[names.variants]` count as one) and the same first given name, ignoring case and accents, and who were born within two years of each other or, when either has no recorded birth year, have an event at the same place. People with no recorded surname or given name, and two people already linked by any recorded relationship, are never paired. Each pair shows both names, linked, with their lifespans and record IDs, the places they have in common and a **Compare** link (`compare.html?a=<id>&b=<id>`). The pairs are leads for a researcher to check against the records, not suggestions to merge anyone: two records may describe one person, or two people who shared a name. They are listed by surname, then name, 100 to a page (`duplicates/page-<n>.html`), up to 500; past 500 the page says how many pairs were found. Only public records are used, so a withheld person is never paired or counted. Remove the setting and rebuild to take the pages down.

When the case has public DNA branches ([Record DNA branches](research.md#record-dna-branches)), the build adds a **DNA** page, listed last under Research in the sidebar. Its title defaults to "DNA"; give the project's own word, up to 60 characters:

```toml
[site]
dna_heading = "Y-DNA"
```

`[project].case_directory` and `default_case` select the case; use the CLI `--case` option for a different one. Existing catalogue/maps/timelines format/output settings control compatible standalone exports as well as the cohesive website built by the CLI.

## Build and inspect

```sh
genealogy --project my-family validate
genealogy --project my-family build
python -m http.server 8000 --bind 127.0.0.1 --directory my-family/dist
```

`build --output OTHER_DIRECTORY` selects another output. Use a dedicated output folder, never a directory containing your raw inputs or case files.

Every page and download is generated from the same privacy-filtered projection, so a withheld person is absent from HTML, search, maps, data files, the GEDCOM download and the sitemap alike. Labels such as "Unassessed tree link" or "tree-marked uncertain" link to `evidence.html`, which explains them. Every label is drawn as one kind of badge, linked to its entry there: confidence, project grades, claim and research statuses, record quality, finding types and the before → after chips of a finding's changes. Its entry decides its colour and a small glyph, printed as hidden text beside the words: ✓ documented or supported, ~ probable, ? possible, ○ unassessed or asserted, ✕ disproved, disputed or rejected, ◇ the supplying tree's own mark (a badge of its own beside the project's label). Types and research statuses are neutral and carry no glyph, because they say what something is, not how far it is believed. The words always carry the label, so nothing depends on colour or glyph, and the stored values stay in `data-status`, `data-confidence`, `data-grade` and similar attributes.

A connection follows stored relationships and their uncertainty; it is not proof of kinship. The coordinate map uses a bundled low-resolution Natural Earth basemap; it is not a street map. Missing coordinates remain missing. Approximate dates retain their supplied text.

Every page shares one frame. The sidebar groups the pages into sections — **People** (the catalogue, families and branches, and possible duplicates when switched on), **Family** (tree, timeline, connections, compare), **Places** (places, statistics), **Records** (sources, reading the evidence), **Research** (research notebook, studies, latest findings, progress) and **About** (site index, and corrections when configured) — each with a small icon; a section's link opens its first page, and only the current section lists its pages, with the current page marked (`aria-current`), so every page stays small. A person's, study's, place's or paged list's page counts as part of the page that lists it. **Find a connection** and **Site map** sit below the sections. On a phone the sidebar folds behind **Menu**; without JavaScript it is always open. The top bar shows a breadcrumb (`Home / People / Ada Fable` on a dossier), a build stamp ("Catalogue · 27 Sep 2026") dated from the newest public finding's `recorded_on` or study's `updated_on`, never the clock, and left out when neither exists, and the site search.

All site assets are local and links are relative. Every page has a **Search the site** box in the top bar; with JavaScript, ⌘K or Ctrl+K anywhere, or `/` outside a text field, moves to it, and its results open in a panel over the page. With JavaScript it loads `data/search-index.js` the first time it is used and lists the 12 best title matches, grouped as people, places, studies, sources, findings and research questions: a title starting with what was typed first, then a word starting with it, then a title containing it. The down arrow moves into the results, the arrows move between them, Enter opens the best match (or the one chosen) and Escape closes the list. Without JavaScript, or when nothing matches, the box searches the people catalogue (`catalogue.html?q=`). Test both desktop and mobile before publication. Core records remain readable without JavaScript, while filtering, graph exploration, comparison and connection tools need it. The interactive pages load one shared `data/site-data.js` script, so they also work when the folder is opened directly from disk (`file://`) and the browser caches the data once for the whole site.

Pages name every record in words. Dates read as a reader writes them ("24 May 1731", "c. 1801", "1754" for a date recorded to the year; see [Date precision](research.md#date-precision)), with the recorded value kept in the markup. A family link reads the right way round ("Ada Fable is the mother of Cara Fable", "Ada Fable and Bram Fable are spouses"), as does each step of a connection ("Cara Fable is the daughter of Ada Fable"). A reference to a place, event, source, claim or finding shows its name ("Death of Ada Fable, c. 1808"), never its record ID; the record ID stays on each dossier and place page as small "Record ID: …" text. Connected groups on **Families & branches** and **Research progress** are named after their earliest-born person ("Group of 42 people around Ada Fable"), and short lists of places, events, names or relatives are shown as pills.

### Large sites

Past 300 people, events, sources or studies, or 100 places (300 relationships, claims or findings for those lists), a site stops writing every record into its tool pages, so each page stays small:

- The catalogue writes its first 50 people; `catalogue/page-<n>.html` holds the rest in name order, in the same table. With JavaScript, search, filters and pages cover everyone from `data/site-data.js`.
- The timeline lists its decades; `timeline/<decade>s.html` (and `timeline/undated.html`) holds each decade's events, and an event's link points there. With JavaScript, the timeline search covers every event.
- Places lists its countries and regions and the cards of the 100 places with the most people; `places/<region>.html` holds each region's place cards in name order, 100 to a page. The map is drawn by the script, and the place search and region menu cover every place from `data/site-data.js`.
- Sources writes its first 80 sources; `sources/page-<n>.html` holds the rest in title order. Its record-type table links to `sources/type-<type>.html` (then `type-<type>--2.html` and on), which list each type's sources in title order, 100 to a page. With JavaScript, the search covers every source.
- Studies writes the 100 most recently updated studies; `studies/page-<n>.html` lists every study in title order, starting at `studies/page-1.html` because the studies page itself is in date order. Each study keeps its own page. With JavaScript, the search covers every study's title, summary and linked people; the shared data never carries a study's body.
- Person menus on the tree, compare and connections pages are filled by the script. Relationships and claims are shown on their subject's page, and findings on the findings log and its archive.
- The statistics page lists at most 25 rows per table and counts the rest, and its countries and regions link to their own places pages.
- Records writes its first 100 citations, in year order; `records/page-<n>.html` holds the rest. With JavaScript, its search, filters and sort cover every citation from `data/records-index.js`.
- The DNA page lists every root branch and, below them, branches and placed people until about 25 KB each (and at most 300 people), counting the rest; each branch's page lists its own people (to about 40 KB) and child branches, and every dossier names its person's branch.

The paged pages are plain lists that need no script.

## Check the links before publishing

```sh
genealogy --project my-family check-links
```

This checks every internal link, image, script, refresh redirect and `#anchor` in `dist/` the way a plain static server resolves them, and exits non-zero when something points at nothing. A link to `page` that exists only as `page.html` is reported, because many hosts do not add the extension. When you add your own hand-written pages, record any known breakage once with `--baseline known-links.json --update-baseline`. From then on only new breakage fails, and later updates only ever remove pairs. The checker is also importable as `genealogy.sitecheck` for projects with their own site builders.

## Rebuilds

Builds overwrite their owned outputs. The `.genealogy-site-manifest.json` tracks generated files, allowing obsolete person pages to be removed when people become private or are removed, and a moved page, `data/redirects.json` or `_redirects` once no former ID needs it. Unrelated files outside that manifest are preserved. Do not hand-edit generated person pages; put durable research into the case.

The progress history is the one output a build reads back: build into the same output folder each time (or copy the previous `data/progress-history.json` into a fresh one first), or the history starts again.

Deployed hosting must also remove obsolete pages. Replace the old site directory with the reviewed new build, or use your host’s delete/synchronization option. Simply copying new files over an old deployment can leave a withdrawn person page accessible.

## Static hosting

Deploy only the contents of the reviewed `dist/` folder to your static host or web server. The toolkit needs no application server, database, external scripts, font provider, analytics, or geocoding service. It supports a URL subdirectory because links are relative.

Moved person pages work on any host: the page at the old address sends the browser on. Hosts that read a `_redirects` file can answer with a real 301 redirect instead, which search engines follow best. Cloudflare Pages applies these rules even though the moved page exists. Netlify serves an existing file in preference to a rule, so there the moved page still does the redirect; to have Netlify answer with the 301, change `301` to `301!` in your deployment step. The build owns `_redirects` while it writes one, so keep other redirect rules in your host's own configuration.

The package does not automatically deploy, create hosting accounts, upload research, or edit WikiTree. Keep the local upload server private; it is not a production hosting server. The same distinction applies to research bundles: a complete bundle is private, even if its corresponding website is public.
